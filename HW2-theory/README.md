# تمرین HTTP – تئوری

## سوال ۱

### تفاوت نسخه‌ها
- نسخهٔ 0.9: فقط GET بود، بدون header و status code و فقط HTML. بعد از هر response اتصال بسته می‌شد.
- نسخهٔ 1.0: مفهوم header و status code و Content-Type اضافه شد، پس غیر از HTML هم می‌شد فرستاد. هنوز هر request یک اتصال TCP جدید می‌خواست.
- نسخهٔ 1.1: اتصال persistent (keep-alive) پیش‌فرض شد و header با نام Host اجباری شد تا virtual hosting ممکن شود. قابلیت chunked transfer و cache بهتر (Cache-Control و ETag) و متدهای PUT و DELETE و OPTIONS هم آمد.
- نسخهٔ 2: فرمت پیام binary شد و چند stream روی یک اتصال TCP می‌رود (multiplexing). همچنین header با HPACK فشرده می‌شود. مشکل head-of-line blocking در سطح TCP هنوز هست.
- نسخهٔ 3: روی QUIC و UDP سوار است و هر stream به‌طور مستقل loss recovery دارد، پس head-of-line blocking از بین می‌رود. همچنین TLS 1.3 داخل handshake است و اتصال با connection ID شناخته می‌شود، پس عوض شدن IP اتصال را قطع نمی‌کند.

### چرا HTTP/3 از UDP استفاده می‌کند؟
پروتکل TCP داخل kernel و middleboxها پیاده شده و عملاً نمی‌شود آن را تغییر داد. در TCP هم فقط یک byte stream مرتب داریم، پس گم شدن یک packet همهٔ streamهای HTTP/2 را متوقف می‌کند. با UDP می‌شود یک transport جدید (QUIC) در user space ساخت، که هم این مشکل را حل می‌کند و هم سریع به‌روز می‌شود.

## سوال ۲

### الف
در پروتکل stateful سرور اطلاعات کلاینت را بین request‌ها نگه می‌دارد و پیام‌ها به هم وابسته‌اند (مثل session در SSH). اما در stateless هر request کامل و مستقل است و سرور چیزی به خاطر نمی‌سپارد. به این ترتیب scale کردن راحت‌تر است، ولی context باید همراه هر request بیاید.

### ب
پروتکل HTTP از نوع stateless است. برای نگه داشتن state معمولاً از cookie و session ID استفاده می‌شود که به داده‌ی سمت سرور اشاره می‌کند. روش دیگر token مثل JWT در header با نام Authorization است که state داخل خود token امضاشده قرار دارد.

## سوال ۳

### الف
در HTTP فقط کلاینت می‌تواند ارتباط را شروع کند و سرور فقط جواب request را می‌دهد. اما در webhook و chat و alerting باید سرور هر وقت event رخ داد خبر بدهد، و کلاینت نمی‌داند کِی باید بپرسد.

### ب
- روش polling: کلاینت هر چند ثانیه می‌پرسد «خبری هست؟». ساده است ولی بیشتر پاسخ‌ها خالی‌اند و تأخیر دارد.
- روش long polling: سرور request را باز نگه می‌دارد تا داده برسد، بعد جواب می‌دهد و کلاینت دوباره request می‌فرستد. تأخیرش کم است ولی هر کلاینت یک اتصال را اشغال می‌کند.
- روش SSE: یک response طولانی با Content-Type برابر text/event-stream که سرور event‌ها را روی آن می‌فرستد. فقط از سرور به کلاینت کار می‌کند.
- روش WebSocket: با Upgrade اتصال به یک کانال دوطرفه تبدیل می‌شود. برای chat عالی است ولی مدیریت اتصال‌ها و scaling سخت‌تر است.
- روش webhook: برای ارتباط سرور به سرور است. گیرنده یک callback URL می‌دهد و سرور مبدأ هنگام event یک POST به آن می‌زند، پس گیرنده باید endpoint عمومی داشته باشد.
- روش push notification: مثل FCM و APNs برای موبایل، که دستگاه یک اتصال دائمی با سرویس واسط دارد. همچنین HTTP/2 server push به این کار نمی‌خورد و منسوخ شده است.

## سوال ۴: اجزای URL

```
ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1
```

- بخش scheme برابر `ss` است.
- بخش userinfo برابر `asghar:1234!!` است (username برابر `asghar` و password برابر `1234!!`).
- بخش host برابر `ss.myproxy.com` است.
- بخش port برابر `1234` است.
- بخش path و query خالی هستند.
- بخش fragment برابر `shadowSocks1` است. این بخش فقط برای نام‌گذاری است و به سرور فرستاده نمی‌شود.

## سوال ۵: انتخاب status code مناسب

1. مشکل دیتابیس ← کد 503 Service Unavailable. دلیل این است که سرویس موقتاً در دسترس نیست، و 500 بیشتر برای خطای غیرمنتظره است و البته مشکل سمت سرور است.
2. نبودن username ← کد 401 Unauthorized. دلیل این است که login رد شده، و پیام را مثل password اشتباه می‌گذاریم تا وجود username لو نرود (پس 404 نه).
3. انتقال سایت به دامنهٔ دیگر ← کد 301 Moved Permanently. دلیل این است که انتقال دائمی است، و برای API با متد POST بهتر است 308 باشد تا متد عوض نشود.
4. رد شدن از rate limit ← کد 429 Too Many Requests.
5. تمدید موفق token ← کد 200 OK. دلیل این است که فقط یک request موفق است و منبع جدیدی ساخته نشده.
6. رنج IP تحریم‌شده ← کد 451 Unavailable For Legal Reasons. دلیل این است که دسترسی به خاطر الزام قانونی بسته شده، و 403 گزینهٔ عمومی‌تر است.

## سوال ۶: تعیین نوع proxy

1. استفاده از mirror دانشگاه برای apt ← forward proxy (از نوع caching).
2. تقسیم request‌ها بر اساس مبدأ جغرافیایی ← reverse proxy در نقش load balancer.
3. احراز هویت برای یک سرویس قدیمی ← reverse proxy.
