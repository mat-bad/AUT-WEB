## سوال اول: Merge و Rebase

### تفاوت
هردو ابزار برای درهم آمیختن تغییرات کامیت‌های مجزا به کار می‌روند. در مرج کامیت‌های برنچ مقصد روی کامبت‌های برنچ مبدا اعمال می‌شوند، اما در ریبیس، برعکس است و ابتدا کامیت‌های برنچ مقصد اعمال می‌شوند به طوری که در نهایت معادل این است که نویسنده برنچ مبدا، کامیت‌های خود را روی کامیت‌های برنچ مقصد زده است.

### موقعیت استفاده
مثلا زمانی که پس از جدا شدن یک feature branch تغییراتی در برنچ اصلی اعمال و دیپلوی می‌شود، بهتر است آن فیچر برنچ تغییرات برنچ اصلی را rebase کند.
ولی هنگام اعمال تغییرات یک feature روی برنچ اصلی، بهتر است این تغییرات با مرج اضافه شوند تا تاریخچه کامیت‌ها منطقی تر باشد و روند مورد انتظاری را طی کند.

## انتخاب بخضی از تغییرات

### هانک چیست؟
در خروجی `diff`، هر **hunk** یک بلوک پیوسته از تغییرات است که با سرصفحه‌ای مثل `@@ -12,7 +12,8 @@` مشخص می‌شود. هر hunk شامل خطوط زمینه، خطوط حذف‌شده (`-`) و خطوط اضافه‌شده (`+`) است.

### بررسی تعاملی و استیج کردن فقط بعضی بخش‌ها
دستور اصلی:

```bash
git add -p
# یا
git add --patch
# برای یک فایل خاص
git add -p path/to/file
```

گیت هر hunk را نشان می‌دهد و می‌پرسد چه کاری انجام شود. انتخاب‌های مهم:

- انتخاب `y` — این hunk را استیج کن
- انتخاب `n` — این hunk را استیج نکن

و ...

برای برگرداندن استیج به‌صورت تعاملی:

```bash
git reset -p
```

### فایده برای ساختن کامیت‌های منسجم
این کار اجازه می‌دهد کامیت‌های اتمیک و منسجم داشته‌باشیم. مثلا این ویژگی را حفظ کنیم که هر کامیت دقیقا یک رفتار جزئی را تغییر دهد، و پروژه بعد از هر کامیت قابل اجرا باشد و در وضعیت inconsistent قرار نگیرد.

## یافتن منشأ خطا


دستور `git bisect` با استفاده از باینری سرچ بین یک کامیت سالم و یک کامیت معیوب، اولین کامیتی که موجب ایجاد خطا شده را پیدا می‌کند.

### مراحل
```bash
git bisect start
git bisect bad                # کامیت معیوب، معمولاً HEAD
git bisect good v1.2          # یک کامیت سالم
# Git یک کامیت میانی را checkout می‌کند
git bisect good   # اگر سالم بود
git bisect bad    # اگر معیوب بود
# تکرار تا پیام: <sha> is the first bad commit
git bisect reset
```

### خودکارسازی
```bash
git bisect run npm test
```
کد خروج `0` یعنی سالم، غیرصفر یعنی معیوب.

### فایده
به جای بررسی خطی همه کامیت‌ها، با سرعت `O(log n)` کامیت خطادار را پیدا می‌کند؛ برای تاریخچه‌های طولانی سریع، دقیق و قابل خودکارسازی است.

## بررسی تغییرات پیش از کامیت

### دستورهای بررسی وضعیت و تفاوت دو دسته تغییرات
```bash
git status     # وضعیت کلی مخزن
git diff       # تغییرات هنوز وارد نشده به staging (working tree vs index)
git diff --cached  # تغییرات آماده‌ی کامیت (index vs HEAD)
# یا معادل:
git diff --staged
```

- تغییرات **unstaged**: تغییراتی که در فایل‌های tracked داده‌اید ولی هنوز `git add` نکرده‌اید. در working tree هستند.
- تغییرات **staged**: تغییراتی که با `git add` به index اضافه شده‌اند و با کامیت بعدی ثبت می‌شوند.

### کامیت معمولی بدون `-a`
فقط **تغییرات staged** کامیت می‌شوند. برای `README.md`:
- بخشی که قبلاً `git add` شده بود، در کامیت می‌آید.
- ویرایش دوم که بعد از staging انجام شده، **unstaged** می‌ماند و کامیت نمی‌شود.

دلیل: `git commit` از snapshot ناحیه‌ی index استفاده می‌کند، نه working tree. گزینه‌ی `-a` فقط فایل‌های tracked را قبل از کامیت به‌صورت خودکار stage می‌کند (untracked را نه).

### جلوگیری از افزودن `tmp/`
در فایل `.gitignore` در ریشه‌ی مخزن بنویسید:
```gitignore
tmp/
```
یا:
```gitignore
tmp/*
```

این تنظیم فقط برای فایل‌های **untracked** اثر دارد. اگر فایلی از قبل tracked باشد، `.gitignore` روی آن اثری ندارد. برای چنین فایلی باید آن را از index خارج کنید:
```bash
git rm --cached path/to/file
git commit -m "Untrack file"
```
پس از آن، `.gitignore` جلوی اضافه‌شدن دوباره‌ی آن را می‌گیرد.

## رفع merge conflict

### ۱. چرا conflict؟ آیا هر تغییر مشترک باعث آن می‌شود؟
خیر. فقط وقتی تغییرات دو شاخه در **یک خط یا ناحیه مشترک** همپوشانی داشته باشند. اینجا هر دو همان یک خط `README.md` را متفاوت تغییر داده‌اند، پس conflict رخ می‌دهد.

### ۲. شناسایی و نقش conflict markers
```bash
git status  
git diff
```

در خروجی `git status` فایل زیر `both modified` دیده می‌شود

داخل فایل:
```text
<<<<<<< HEAD
نسخه برنچ فعلی
=======
نسخه برنچ دیگر
>>>>>>> <reference>
```

### ۳. مراحل تکمیل merge (حفظ هر دو تغییر)
1. فایل را باز کنید، هر دو متن را ترکیب و markerها را حذف کنید.
2.  بررسی نبودن marker:
```bash
grep -R "<<<<<<<\|=======\|>>>>>>>" .
git diff --check
```
3. `git add README.md`
4. `git commit` یا `git merge --continue`


### ۴. لغو merge
```bash
git merge --abort
```

## انتخاب روش مناسب برای بازگرداندن تغییرات

### ۱. دور ریختن تغییرات unstaged فایل `notes.txt`
در این حالت index با آخرین کامیت یکسان است و فقط working tree تغییر کرده. می‌خواهیم فقط همین فایل به حالت کامیت برگردد و بقیه فایل‌ها دست نخورند:

```bash
git restore notes.txt
```

### ۲. خارج کردن `notes.txt` از staging بدون از دست دادن ویرایش‌ها
تغییرات را `git add` کرده‌ایم ولی هنوز کامیت نکرده‌ایم. می‌خواهیم از index خارج شود ولی ویرایش‌ها در working tree بمانند:

```bash
git restore --staged notes.txt
```

در این حالت برای این فایل index به HEAD برمی‌گردد، working tree دست نمی‌خورد و تاریخچه تغییری نمی‌کند.

### ۳. خنثی کردن یک کامیت معمولی که push شده
کامیت روی `main` مشترک push شده و هم‌تیمی‌ها هم آن تغییر را در تاریخچه‌ی خود اعمال کرده‌اند. باید بدون بازنویسی تاریخچه اثر آن را برگردانیم پس از این دستور استفاده می‌کنیم:

```bash
git revert <commit-hash>
```

یک کامیت جدید می‌سازد که تغییرات آن کامیت رابرمی‌گرداند. تاریخچه حفظ می‌شود و یک کامیت جدید برای این تغییر ایجاد می‌شود که مانند هر کامیت دیگری می‌توان آن را push کرد.

چرا force push و حذف کامیت مناسب نیست؟
 چون `main` مشترک است و بازنویسی تاریخچه کامیت‌های آن force push می‌تواند  push آن‌ها را رد کند.
 یا در حالت بدتر درصورتی که آنها `git rebase origin/main` انجام دهند، ممکن است کامیت حذف شده در برنچ آنها باقی بماند و در آینده دوباره در `main` ظاهر شود.
