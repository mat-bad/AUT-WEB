## سوال اول: Merge و Rebase

### تفاوت
هردو ابزار برای درهم آمیختن تغییرات کامیت‌های مجزا به کار می‌روند. در مرج کامیت‌های برنچ مقصد روی کامبت‌های برنچ مبدا اعمال می‌شوند، اما در ریبیس، برعکس است و ابتدا کامیت‌های برنچ مقصد اعمال می‌شوند به طوری که در نهایت معادل این است که نویسنده برنچ مبدا، کامیت‌های خود را روی کامیت‌های برنچ مقصد زده است.

### موقعیت استفاده
مثلا زمانی که پس از جدا شدن یک feature branch تغییراتی در برنچ اصلی اعمال و دیپلوی می‌شود، بهتر است آن فیچر برنچ تغییرات برنچ اصلی را rebase کند.
ولی هنگام اعمال تغییرات یک feature روی برنچ اصلی، بهتر است این تغییرات با مرج اضافه شوند تا تاریخچه کامیت‌ها منطقی تر باشد و روند مورد انتظاری را طی کند.

## انتخاب بخضی از تغییرات

### hunk چیست؟
در خروجی `diff`، هر **hunk** یک بلوک پیوسته از تغییرات است که با سرصفحه‌ای مثل `@@ -12,7 +12,8 @@` مشخص می‌شود. هر hunk شامل خطوط زمینه، خطوط حذف‌شده (`-`) و خطوط اضافه‌شده (`+`) است.

### بررسی تعاملی و استیج کردن فقط بعضی بخش‌ها
دستور اصلی:

```bash
git add -p
# یا
git add --patch
# برای یک فایل خاص
git add -p path/to/file
```

Git هر hunk را نشان می‌دهد و می‌پرسد چه کاری انجام شود. انتخاب‌های مهم:

- `y` — این hunk را استیج کن
- `n` — این hunk را استیج نکن

و ...

برای برگرداندن استیج به‌صورت تعاملی:

```bash
git reset -p
```

### فایده برای ساختن کامیت‌های منسجم
این کار اجازه می‌دهد کامیت‌های اتمیک و منسجم داشته‌باشیم. مثلا این ویژگی را حفظ کنیم که هر کامیت دقیقا یک رفتار جزئی را تغییر دهد، و پروژه بعد از هر کامیت قابل اجرا باشد و در وضعیت inconsistent قرار نگیرد.
